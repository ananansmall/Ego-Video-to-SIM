## 0. 摘要（先给结论）

1. **夹爪轨迹 = MANO 手形重定向出来的**，不是规划出来的。链路是：
   `MANO FK → 坐标链(cam→GLB/SAPIEN) → svd_palm 解算姿态 → 重力对齐 → 平滑 → 连续性修正 → pre_translate(常量平移) → neutral offset`。
   位置可以小幅优化，**姿态必须跟随 MANO**（这是用户反复强调的口径）。

2. **`svd_palm` 的当前定义**：取 MANO 5 个点（拇指PIP、食指MCP/PIP/DIP/尖）做**手掌平面 SVD**得 Z 轴，
   用"食指 MCP→PIP"做 X 轴候选并 Gram-Schmidt 正交化，Y=Z×X、Z=X×Y；`pos = 手掌锚点`；
   最后交给 `align_gripper_approach_to_gravity` 保证 X（接近轴）朝下。

3. **"上下翻转"没解决，是真的**，而且**不是一个问题，是三个不同性质的问题被混在一起**：
   - **(a) 分支翻转**：X·g 过零硬阈值（`dot(X,g) < 0`）逐帧独立决策 ⇒ 帧间 180° 台阶。
   - **(b) 绕 X 的 roll 翻转**：X 已朝下，但**闭合轴 Y 反向** ⇒ 两指左右对调 / 闭合轴变竖直（"上下夹"）。
   - **(c) 欧拉角表示环绕**：R 本身连续，但 ZYX 欧拉在 ±180° 处环绕 ⇒ 看起来像翻转。

   现在共有 **6 处**独立补丁分别处理它们，各自判据/参考/阈值都不同 ⇒ 互相打架、覆盖、失效。
   其中**处理 (a) 分支台阶的那一处（`unflip_rotation_traj_continuity`）目前是死代码**，
   挂在一条无人调用的链（`smooth_gripper_traj` ← `_smooth_mano_traj`）上 ⇒ **180° 台阶根本没被处理**（§3.4 已核实）。

   **今天（2026-09-20）实测仍能看到症状**：Stage1 选出的位姿
   `闭合轴=[-0.037,-0.712,-0.702] 竖直度=0.70 → 判定"上下夹"，姿态分被清零`（见 §3.5 证据）。

4. **我的判断**：这个问题**不可能**靠继续加补丁解决，而且当前的"补丁"里有一条**根本没接线**。
   优先顺序建议：**① 先让姿态分支的处理真正生效（或统一成一处）→ ② 把分支符号作为显式状态落盘 → ③ 给"左右夹"加硬门**。
   §5 给了三条可验收的硬指标 + §6 给了改进方向。

## 1. 夹爪轨迹是怎么来的（完整链路）

### 1.1 输入

| 输入 | 内容 |
|---|---|
| `~/data/hawor/7a` | MANO 的 `pred_rot` / `pred_hand_pose` / `pred_trans` + 相机 `R_c2w / t_c2w`（113 帧） |
| `~/data/ras/7_vggt_omega` | `transform_params.npz`：`scale_ratio` / `R_hand_to_glb` / `t_hand_to_glb` |
| 目标物体 | GLB 场景 + 目标 actor 名称（默认 `glb_4`）+ scale |

### 1.2 逐帧解算（每帧一次）

```
① MANO FK                      → 21 关节 (相机系)            data_loader.compute_mano_joints()
② 坐标链（grasp_hawor._mano_to_sapien）
     p_hw  = R_c2w[f] @ p_cam + t_c2w[f]        ← **逐帧真实相机位姿**（不要用固定近似）
     p_glb = s · R_h2g @ p_hw + t_h2g           ← 相似变换到 GLB（= SAPIEN 世界）
③ 夹爪姿态解算（svd_palm，见 §2）              data_loader.compute_mano_based_gripper_pose()
④ 重力对齐                                     physics_utils.align_gripper_approach_to_gravity()
⑤ 平滑（**实际生效的是"重定向前对 MANO 关节做 SG(17,2)"**，见 §3.4）
⑥ R 连续性 unflip（只在 |X·g| ≤ 0.15 模糊带）   physics_utils.unflip_rotation_traj_continuity()
     ⚠️ **当前未生效（死代码）** —— 见 §3.4 的核实
⑦ 时间连续性：帧间 closing 轴 Y 反向 ⇒ 绕 X 转 180°（保重力）  grasp_hawor.py:2048-2056
⑧ pre_translate：求一个**常量平移**，把 F50 的手掌锚点挪到目标物体中心  grasp_hawor._pre_translate_mano_trajectory()
⑨ neutral_offsets：残余对齐偏移               grasp_hawor._compute_neutral_offsets()
⑩ dump：output/<run>/preprocess_traj.npz      grasp_hawor._dump_preprocess_traj()
```

### 1.3 产物与消费方式

`preprocess_traj.npz` / `self._mano_gripper_traj[side]` 关键字段：

| 字段 | 形状 | 含义 |
|---|---|---|
| `pos` | (N,3) | 夹爪 base（= 手掌锚点）位置（GLB/SAPIEN 世界系，已 pre_translate） |
| `R` | (N,3,3) | 夹爪姿态，列 = [X(接近/手指伸出), Y(开合), Z] |
| `j1`,`j2` | (N,) | 两指关节值（由 MANO 指尖距得到，钳在 [0,0.05]） |
| `joints` | (N,21,3) | MANO 参考点（供可视化/对拍） |

三个 Stage 对它的用法：

| Stage | 用哪一段 | 用途 |
|---|---|---|
| Stage1 | 扫描 `F(grasp_frame) ± 15` 的**每一帧姿态**作为候选；位置另配微调 | 求 anchor 位姿 |
| Stage2 | **前缀** `MANO_FOLLOW` 原样回放 + 中段改成"轴向直线逼近" | 接近与抓取 |
| Stage3 | **后缀** 携带到 `release_candidate` | 搬运与释放 |

> **关键约束**：轨迹的**形状（位置序列）**可以小幅优化，**姿态只能跟随 MANO**。
> 用户口径："参考的 mano 是一定要跟随的…可以稍微调整它的位置，但姿态要跟上"。
> 因此凡是"改姿态"的处理（§3 的 6 处补丁）本质上都是**在不改姿态的前提下对齐符号分支**。

## 2. `svd_palm` 的当前定义（逐步）

代码：`data_loader.compute_mano_based_gripper_pose(joints_sapien, prefix, finger_origin_x=0.03689)`

```python
# ① 锚点：拇指 PIP 与食指 MCP 的中点
anchor = (j[3] + j[5]) / 2

# ② 手掌平面：5 点 SVD，最小奇异值方向 = 平面法向 = Z
palm_pts = [j[3], j[5], j[6], j[7], j[8]]          # 拇指PIP + 食指MCP/PIP/DIP/尖
centered = palm_pts - mean
_,_,Vt = svd(centered)
z_axis = Vt[2] / ||Vt[2]||

# ③ Z 的符号：SVD 符号逐帧可任意翻 ⇒ 用解剖学叉乘 n_ref 做**确定性符号约定**
n_ref = cross(index_pip - index_mcp, index_mcp - thumb_pip)
if prefix == "left": n_ref = -n_ref        # 左手镜像，叉积方向相反
if dot(z_axis, n_ref) < 0: z_axis = -z_axis

# ④ X 轴候选 = 食指 MCP→PIP，再对 Z 做 Gram-Schmidt
x_raw = normalize(index_pip - index_mcp)
x_axis = normalize(x_raw - dot(x_raw, z_axis) * z_axis)

# ⑤ 严格正交：Y = Z × X, Z = X × Y
R = column_stack([x_axis, y_axis, z_axis])

# ⑥ 重力对齐：X 朝上 ⇒ 绕 Y 翻 180°
R = align_gripper_approach_to_gravity(R)

# ⑦ 位置与手指关节
root_pos = anchor                                     # 无偏移（对齐 viz_web）
joint = clamp(||index_tip - thumb_tip|| / 2, 0, 0.05)  # 两指同值
```

### 2.1 与另一条实现（`analytical`）的对比

| 项 | **svd_palm**（默认，v51 U1） | `analytical`（仅作对照保留） |
|---|---|---|
| 输入点 | 5 点（拇指PIP + 食指4点） | 3 点（腕、finger1、finger2 指尖） |
| 姿态解算 | 手掌平面 **SVD + Gram-Schmidt** 显式构轴 | **加权 Procrustes**（Y 轴权重 W_Y=5） |
| X 轴 | 食指 MCP→PIP | wrist→指尖中点 `pointing` |
| 位置 | `anchor` = 手掌锚点 | `finger_mid − R @ finger_mid_in_gripper` |
| 手性处理 | `n_ref` 左手取反 | `y_sign = −1`（v6.0 统一） |
| 重力对齐 | ✓（同一函数） | ✓（同一函数） |
| 备注 | Stage1 的 anchor 就是它；`--grasp-pose-method` 可切换 | 旧链，历史兼容 |

### 2.2 这套定义里**先天**无法保证的三件事

| # | 无法保证 | 后果 |
|---|---|---|
| 1 | **X（接近轴）的符号**只能靠事后判 `dot(X,g)` 来翻 | 过零处会抖 ⇒ 180° 台阶（问题 a） |
| 2 | **Y（开合轴）的方向**完全没约束（只靠"帧间连续"） | X 朝下 + Y 竖直是自洽解 ⇒ "上下夹"（问题 b） |
| 3 | **Z 的符号**只保证"与手掌解剖法向同向" | 手掌法向是**解剖学**量，与"是否朝下"无必然联系（代码注释里已明确写过这一点） |

> 注：代码里已明确写了"翻转 Z（等价于绕 X 转 180°）只反向开合方向，手指仍朝天"，
> 也就是说**早期曾误以为修 Z 符号就能解决朝上**——这个误解留下的痕迹在后面几处补丁里还能看到。

## 3. "上下翻转"问题拆解：其实是三个问题

### 3.1 (a) 分支翻转（整帧 180°，X 轴朝上 ↔ 朝下）

**机制**：`align_gripper_approach_to_gravity` 是**逐帧、无状态、硬阈值**：
`dot(X, g) < 0 ⇒ R = R @ diag([-1,1,-1])`。

**症状**：当 MANO 的 approach 轴接近**水平**时，`dot(X,g)` 在相邻帧间正负跳变 ⇒ 姿态序列出现真实的 180° 台阶。
实测（v1 文档记录）：`F7→F8 179.5° | F9→F10 179.1° | F13→F14 178.8° | F108→F109 179.3°`，而全序列平均帧间变化只有 7.63°。

**危害**：1 个控制周期（33ms）内命令 180° 翻转 ⇒ PD 跟不住 ⇒ 基座姿态滞后 11~48°、角速度 589°/s ⇒ 手指扫偏厘米级 ⇒ 撞上物体。

**现有处理**：`unflip_rotation_traj_continuity`（`physics_utils.py:274`）
- **只在 `|dot(X,g)| ≤ 0.15` 的模糊带内**允许翻回"与上一帧更近"的分支；
- 带外**保持**重力对齐结果不动（否则会翻掉 97/113 帧，让 `R[F50]` 被翻 ⇒ pre_translate 偏移错 ⇒ 整条轨迹偏离 12cm）。

**遗留缺陷**：
1. **该函数在当前管线里根本没被执行**（死代码，见 §3.4 核实）⇒ 180° 台阶**原样保留**。
2. 即便接上：模糊带宽度 `0.15`（≈8.6°）是**手调的**，带边缘仍是硬切换；
3. 它只覆盖 `mano_smoothing` 那一次，**Stage2 用的那条轨迹上不会再跑它**。

### 3.2 (b) 绕 X 的 roll 翻转（X 已朝下，但 Y 反向）

**机制**：`X` 朝下只约束了 2 个自由度；**绕 X 的 roll（Y/Z 的朝向）完全自由**。
Y 反向 = 两指左右对调，Z 反向；视觉上就是"夹爪反了/上下夹"。

**症状（v2 会话实测，代码注释）**：
```
闭合轴 = [0.043, -0.686, -0.726] → 竖直度 0.73  ✗   ("上下夹")
[Stage2 track] MANO_FOLLOW rot=17.51/169.02deg   ✗   (均值好, 峰值 169°)
[Stage1 CSV]   命令朝上=0 ✓ 实际朝上=0 ✓              (Stage1 本身正常)
```
⇒ "夹爪反了"只出现在 **Stage2 的 `MANO_FOLLOW` 段**（前缀开头几帧 + 后缀末尾几帧），与用户观察完全吻合。

**现有处理（3 处，互不知情）**：

| 位置 | 做法 | 参考基准 |
|---|---|---|
| `grasp_hawor.py:2048-2056`（预处理） | 帧间 Y 点积 <0 ⇒ 绕 **X** 转 180°（Y,Z 反号，X 不动） | **上一帧** |
| `stage2_reconstruct_mixin.py:810-842` | ① 逐帧"强制朝下"（X·g<0 ⇒ `align_…`）；② 以**末帧 Y** 为基准把整段反向的 Y 翻回来 | **末帧 Y** |
| `physics_utils.py:253`（`_GRIP_CLOSE_AXIS_HORIZONTAL=1`） | 绕 X 转 θ 让 Y 落进水平面（`θ = atan2(−Y·g, Z·g)`） | **世界重力** |

### 3.3 (c) 欧拉角表示环绕（不是真翻转，但看起来一样）

**机制**：R 连续，但 ZYX 欧拉在 ±180° 处环绕。实测：
```
[Stage2 cmd] MANO_FOLLOW 原始 rz [-119.1, 59.2] deg, **段内最大跳变 178.31°** ✗
```
**现有处理**：`data_loader.zyx_euler_continuous`（锁 ±15°）——Stage2/Stage3 已用；
但 Stage3 早期用 `rotmat_to_zyx_euler` **单支直取**，相邻命令 rz 跳变 179.59° ✗（v2 已修，改用同源连续化）。

### 3.4 六处补丁的总览（这就是"没解决"的根源）

| # | 位置 | 处理对象 | 判据 | 参考 | 阈值 | 当前是否生效 |
|---|---|---|---|---|---|---|
| 1 | `physics_utils.align_gripper_approach_to_gravity` | 分支(a) | `dot(X,g)<0` | 世界重力 | 0（`up_tilt_deg` 保留但默认 0） | ✅ **生效**（被 SVD 解算每帧调用） |
| 2 | `physics_utils.unflip_rotation_traj_continuity` | 分支(a) 台阶 | `\|dot(X,g)\|` | **上一帧 R** | 0.15 | ❌ **死代码**（唯一调用点在 #3 里，而 #3 从未被调用） |
| 3 | `mano_smoothing.smooth_gripper_traj:212` 调用 #2 | 同上 | — | — | — | ❌ **死代码**：`smooth_gripper_traj` 只被 `grasp_hawor._smooth_mano_traj()` 调用，而 `_smooth_mano_traj()` **全仓无调用点** |
| 4 | `grasp_hawor.py:2051` | roll(b) | `dot(Y_i, Y_{i-1})<0` | **上一帧 Y** | 0 | ✅ 生效（在 `run()` 预计算里） |
| 5 | `stage2_reconstruct_mixin.py:817` + `:837` | 分支(a)+roll(b) | `dot(X,g)<0` / `dot(Y_i, Y_last)<0` | **世界重力 + 末帧 Y** | 0 | ✅ 生效（仅 Stage2 前缀） |
| 6 | `physics_utils.py:253`（opt-in） | roll(b) | `Y·g ≠ 0` | 世界重力 | 1e-6 | ⚠️ 仅 `_GRIP_CLOSE_AXIS_HORIZONTAL=1` |

**已核实的两个关键事实（2026-09-20 grep 全仓确认）**：

```bash
$ grep -rn "_smooth_mano_traj\|smooth_gripper_traj" --include=*.py .
grasp_hawor.py:103:  from mano_smoothing import smooth_gripper_traj, smooth_joints_seq
grasp_hawor.py:4902: def _smooth_mano_traj(self, side):
grasp_hawor.py:4908:     ok = smooth_gripper_traj(self._mano_gripper_traj, side)
mano_smoothing.py:179: def smooth_gripper_traj(...)
# ⇒ smooth_gripper_traj 只被 _smooth_mano_traj 调用；_smooth_mano_traj 无任何调用点
```

1. **`unflip_rotation_traj_continuity`（处理 180° 台阶的那一处）在当前管线里从未被执行** ——
   它挂在 `smooth_gripper_traj` 里，而 `smooth_gripper_traj` 只被
   `GraspSimulator._smooth_mano_traj()` 调用，该方法**全仓没有任何调用点**（死代码）。
   （历史上 `mano_smoothing.py:206` 的注释还专门写过"该修复函数此前已写好但全仓无任何调用点(死代码) — 这里接线"，
   说明它至少被判定过"已接线"，但现在**又断开了**。）
2. 因此**实际生效的平滑只有** `smooth_joints_seq`（对 MANO **关节**做 SG(17,2)，且 min-jerk 已于 2026-09-06 移除），
   它在**重定向前**跑（`grasp_hawor.py:1924 / 2003`）。
   **重定向之后（也就是"重力对齐 + SVD 定符号"之后）没有任何姿态连续性修正。**

**⇒ 这就是"上下翻转没解决"的一个直接机制**：
180° 台阶是在**重力对齐那一步**产生的（在重定向前后的 SVD 解算里），
而"消除台阶"的代码却在**下游且未接线** ⇒ 台阶原封不动进入 Stage2 的 `MANO_FOLLOW`，
于是就有了 `rot=17.51/**169.02**deg` 那种"均值好、峰值爆"的跟踪误差。

**另一个问题**：同一帧可能被 #1→#4→#5→#6 依次处理，每次都可能翻 180°；
而它们的**参考帧不同**（上一帧 / 末帧 / 世界重力），
**⇒ 一处"修正"很可能把另一处的结果又翻回去**。
更糟的是：**Stage1 还得在 reward 里显式惩罚"翻转解"**（`stage1_grasp_mixin.stage1_reward` 的 `_flip` 清零），
说明连 Stage1 都被迫为这件事打补丁。

### 3.5 今天的实测证据（问题仍然存在）

`output/cctrav3/stage1/grasp.log`（2026-09-20，`--side left`，`scale=0.5`，CoACD 64 凸包）：

```
[Stage1 姿态] 闭合轴=[-0.037, -0.712, -0.702] 竖直度=0.70 水平度=0.30 方位角=-92.9°
              | 对齐目标(水平轴, 边长45mm) align=0.037 → 有效=0.011 (+0.1分)
[Stage1 反向告警] 闭合轴 [-0.037,-0.712,-0.702] 竖直度=0.70 (>0.5) → **上下夹** ✗
                 本候选姿态分已被清零 (对齐项=0.037, 水平项=0.298)
```

解读：
- 期望：闭合轴**水平**且对齐物体的**水平最短轴**（边长 45mm）⇒ `align` 应接近 1。
- 实测：`align=0.037`（≈0），`竖直度=0.70` ⇒ **闭合轴几乎竖直 ⇒ 上下夹**。
- 也就是说：**Stage1 遍历了 7533 个候选，选出来的"最优位姿"在姿态上是"上下夹"的**，
  只能靠 reward 把这一项清零来"止损"，而不是让它变对。

⇒ **"上下翻转没解决"的直接后果就是：Stage1 给出的 anchor 姿态本身不是"左右夹"的正确姿态**，
这与用户第 2 点判断完全一致（"stage1 没法给出正确的位姿，是很难实现的"）。

## 4. 为什么"还是没解决"——我的分析（可能的问题清单）

### 4.1 判据不统一（首要原因）
五个"朝下/连续"的判据各自用了**不同参考**：世界重力 / 上一帧 / 末帧 / 手掌解剖法向 / F50。
只要参考不同，就存在"甲说对、乙说反"的帧，翻来翻去。

**建议**：只保留**一个**"姿态分支"定义（见 §6.1），其余全部删除或退化为**只告警**。

### 4.2 硬阈值的过零抖动（问题 a 的根）
`dot(X,g) < 0` 在 X 接近水平时逐帧独立决策 ⇒ 必然抖。
模糊带（`direction_eps=0.15`）只是把抖动窗口变窄，**没有消除**；而且带外仍然硬切。

**建议**：把"是否翻转"变成**沿轨迹传播的状态**（当前分支 + 切换代价），
即"最小化整段翻转次数"的动态规划/贪心，而不是逐帧比大小。

### 4.3 三段各自为政（Stage0 / Stage1 / Stage2 各改一遍）
- Stage0（预处理）改一次 ⇒ 改的是"参考轨迹"；
- Stage1 在它上面再搜 ±5°~±15°，`reward` 里再用"与 F50 闭合轴反向 ⇒ 对齐分清零"兜一次（**软约束**）；
- Stage2 的 `MANO_FOLLOW` 前缀又"强制朝下 + roll 归一"一次（**硬改命令**）。

**风险**：Stage2 命令与 Stage1 anchor 的一致性只靠 digest 比对，
**看不出"符号分支"是否一致**；一旦不一致，物理上就是 169° 的姿态误差。

**建议**：把"分支符号"（X 的 ±、Y 的 ±）作为**bundle 的显式字段**一起落盘，
Stage2/3 直接复用，不再各自重算。

### 4.4 `_GRIP_FORCE_DOWN` 的参考是"末帧"（可能自我污染）
`stage2_reconstruct_mixin.py:834` 用 `_Yref = mano_R[-1][:,1]`（**末帧**）作为整段的 roll 基准。
若末帧本身是错的（例如刚好落在模糊带被翻过），**整段都会被带错**。

**建议**：roll 基准不应取单帧，应取**长度加权的主方向**（如对 Y 做符号对齐后的平均/中位数）。

### 4.5 时间连续性修正绕 X 180° 会改掉"闭合轴"（与抓取目标冲突）
第 ④ 处补丁（改 Y 的符号）在原理上等于"把两个手指对调"。
它确实能消除跳变，但会改变"哪根手指在物体哪一侧"，
与 Stage1 里"闭合轴对齐物体水平最短轴"的目标**可能打架**（一个要连续，一个要对齐）。

### 4.6 `_GRIP_CLOSE_AXIS_HORIZONTAL` 的位置很危险
它被放在 **Stage0 的 MANO→夹爪映射链路里**（`align_gripper_approach_to_gravity` 内部）。
一旦打开，它会**改变 Stage0 的输出**（= 改轨迹）⇒ 改 recipe digest ⇒ **必须重跑 Stage1**，
而且它与 `unflip_rotation_traj_continuity`（模糊带）的作用方向不保证一致。
（v2 成功版恰好打开了它，说明它有效——但它与补丁 #2 的相互作用没有被验证过。）

### 4.7 姿态平滑链路**实际上是断开的**（已核实，优先级高）

现状（grep 全仓确认）：

| 环节 | 代码 | 是否在跑 |
|---|---|---|
| 重定向前：MANO 关节 SG(17,2) | `smooth_joints_seq` @ `grasp_hawor.py:1924 / 2003` | ✅ 在跑（**min-jerk 已被移除**，只去抖） |
| 重定向后：夹爪 R 的四元数 Slerp 平滑 | `smooth_gripper_traj` @ `mano_smoothing.py:179` | ❌ 只被 `_smooth_mano_traj()` 调，而后者**无调用点** |
| 重定向后：R 连续性 unflip（消除 180° 台阶） | `unflip_rotation_traj_continuity` | ❌ 挂在上面那条死链里 |

**后果**：
- 姿态平滑**只在关节层**发生，而"是否朝下/符号分支"的决定发生在**关节层之后**
  （SVD 解算 + 重力对齐）⇒ **翻转不会被平滑掉**；
- `R_continuity` 检查（`_check_mano_R_continuity`，只告警不改）**照常会报 >90° 帧对**——
  如果日志里确实有，就等于"有告警、无人处理"。

**需要做的（二选一，别两边都做）**：
- (A) 重新接线：在 `_preprocess_mano_traj()` 里（`pre_translate` **之前**）调用
  `unflip_rotation_traj_continuity`（或直接替换成 §6.1 的 Viterbi 分支跟踪）；
- (B) 若决定不用它，就把它和 `smooth_gripper_traj` 一起删掉/标注废弃，
  避免下次又"以为在跑"。

**顺带核实项**（低成本）：对 `preprocess_traj.npz` 的 `R` 逐帧断言 `det(R)=+1`、`RᵀR≈I`。

### 4.8 缺少"必须左右夹"的**硬**判据
现在只有 Stage1 `reward` 里的软项（`_horiz`、`_flip` 清零）。
**没有**任何硬门说"闭合轴必须水平（|Y·g| < 阈值）"。
⇒ 只要抬得起，上下夹也能过关 ⇒ 到了 Stage2 变成姿态误差 169°。

**建议**：加一条硬门（Stage1a 预筛 + Stage2 契约门都查）：
`|dot(Y, ĝ)| ≤ 0.35`（即闭合轴与水平面夹角 ≤ 20°），并且 `dot(Y_cand, Y_ref) > 0`（不反向）。

## 6. 改进方向（不动结论，供决策）

### 6.1 【推荐】把"姿态分支"变成显式状态（根治 a + b）
1. 定义**唯一的 canonical 形式**：
   - `X ≡ −ĝ`（接近轴严格朝下）——由 `align_gripper_approach_to_gravity` 保证；
   - `Y ≡ normalize(Ŷ − (Ŷ·ĝ)ĝ)`（把开合轴**投影到水平面**）——由"闭合轴水平化"保证（应**默认开启**）；
   - `Z = X × Y`。
2. 对整条轨迹做**一次性**分支跟踪（不是逐帧比大小）：
   把每帧的两个候选分支（`R` 与 `R@diag([-1,1,-1])`）作为状态，
   用"帧间测地距离之和最小"做**动态规划**（Viterbi）⇒ 全局最优、无抖动、无过零抖。
3. 结果落盘到 `preprocess_traj.npz`（`R` + `branch_sign`），Stage1/2/3 **只读不算**。

### 6.2 把 6 处补丁收敛成 1 处
保留 §6.1 的实现；其余 5 处退化为**断言/告警**（不修改轨迹）。
好处：可审计、可复现、digest 可校验。

### 6.3 Stage1 的姿态搜索限制在"同分支"子空间
现在的 ±5°/±15° 扰动（绕夹爪 Y/Z）**能产生翻转解**，只能靠 reward 清零来止损。
建议在生成候选时就把扰动限制在**不改变 sign(X)、sign(Y)** 的子空间
（即绕 Z 的小角度 = roll 自由；绕 X/Y 严格 ≤ 5° 且做符号检查）。
⇒ "位姿选择权"仍然很多（roll 方向有自由度），但**不会选出上下夹**。

### 6.4 给"左右夹"加硬门（见 §4.8）
Stage1a 预筛 + Stage2 契约门都查 `|Y·ĝ| ≤ 0.35`。
这条一旦加上，"上下夹"就进不了后续流程，也就不需要 169° 的姿态追赶。

### 6.5 把姿态平滑/连续性修正在"正确的层"接上（见 §4.7）
- 现状：只有**重定向前**的关节 SG 在跑；重定向后的 R 平滑与 unflip **都是死代码**。
- 但注意顺序：**不能**用"对 R 做 Slerp 平滑"来消除 180° 台阶 —— 台阶在两分支之间，
  平滑器会把 180° 抹成"中间乱转"（`mano_smoothing.py:207` 已写明"必须在 quat 平滑**之前**做 unflip"）。
- ⇒ 正确顺序：**先做分支跟踪（§6.1）→ 再做旋转域平滑**，并断言 `det(R)=+1`、`RᵀR≈I`。

## 8. 一句话总结

**夹爪轨迹 = MANO 手形的重定向**；`svd_palm` 用 5 点手掌平面 + Gram-Schmidt 定姿态，
**只保证 X（接近轴）朝下，不保证 Y（开合轴）水平、也不保证符号分支唯一**。
"上下翻转"因此被拆成了"分支翻转 / roll 翻转 / 欧拉环绕"三个问题，
现在被 **6 处各自为政的补丁**反复处理 ⇒ 互相覆盖、仍然残留（今天实测：Stage1 选中的位姿
闭合轴竖直度 0.70 = 上下夹，对齐分 0.037 ≈ 0）。
**根治办法 = 把分支符号提升为显式状态、在链路里只算一次、并给"左右夹"加硬门**；
在此之前，Stage1 很难稳定给出"正确的位姿"。
